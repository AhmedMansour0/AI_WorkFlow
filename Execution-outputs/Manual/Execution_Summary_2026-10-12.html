Execution notes
Every result below was produced by running the case against the live instance on 2026-10-12, not inferred from a related case. Two points on the environment. First, the demo is shared and publicly credentialled, and its data moved underneath the run: the system-user count went from 11 to 120 while testing was in progress, so no assertion depends on an absolute record count or a fixed id. Second, this volatility is what finally made TC-ADM-UI-032 executable — pagination needs more than 50 users, and the instance crossed that threshold mid-run. One locator correction is worth recording for the automation phase: the pager is .oxd-pagination__ul, not .oxd-pagination, and the Change Password control is an input[type=checkbox], not a switch.

[OrangeHRM][/web/index.php/auth/requestResetPassword][Password reset response time reveals whether a username exists]
Test case(s): TC-AUTH-UI-022 · Exploration ref: New — found during execution · Requirement: FR-AUTH-5, NFR-SEC
Description:
The password-reset endpoint responds in a measurably different way depending on whether the submitted username exists. A username that does not exist is answered in well under one second with the standard success page, while a username that does exist hangs for about 61 seconds before failing. An unauthenticated attacker can therefore enumerate valid usernames purely from response time, with roughly an 80x separation between the two cases and no need to interpret the response body at all. This compounds BUG-01, which already discloses account state at the login form.
Steps to reproduce:
  1. Open a client with no session and navigate to /web/index.php/auth/requestPasswordResetCode.
  2. Submit the reset form with a username that does not exist, for example “ZzNoSuchUser7777”, and record the elapsed time and response.
  3. Submit the reset form again with a username that does exist, for example “Admin”, and record the elapsed time and response.
  4. Repeat both submissions once more with a second non-existent username to confirm the pattern is stable.
  5. Compare the elapsed times of the existing and non-existing submissions.
Expected Result:
Both submissions return the same response in a comparable amount of time, so that no observable difference reveals whether the username exists.
Actual result:
Non-existent usernames returned HTTP 302 to /auth/sendPasswordReset with the success page in 0.977 s and 0.710 s. The existing username “Admin” hung for 61.485 s and 61.492 s and returned no response. The timing gap is approximately 80x and was stable across all four measurements, giving a reliable username-enumeration oracle.
